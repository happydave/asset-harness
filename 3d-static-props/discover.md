# Discover: image-to-3D static props (Hunyuan3D on `ai2`)

**Status:** completed (pipeline mapped + harness ready; **gated on a model install + a ROCm test**)

## Subject

Local image-to-3D for static props (Sounding: computers, debris, rocks, crates), single concept
image → textured mesh → glTF for Bevy. `ai2` ComfyUI, as of 2026-06-22.

## Motivation

Decide the local 3D-gen path, surface the license picture (3D is where the clean-Apache lane gets
hard), and confirm whether it runs on the AMD gfx1201 card before committing.

## Findings

### Local path exists: Hunyuan3D 2.0 (native ComfyUI) — Confirmed

`ai2` has native Hunyuan3D 2.0 nodes (`ImageOnlyCheckpointLoader`, `CLIPVisionEncode`,
`Hunyuan3Dv2Conditioning`, `EmptyLatentHunyuan3Dv2`, `VAEDecodeHunyuan3D`, `VoxelToMesh`,
`SaveGLB`) and templates (`3d_hunyuan3d_image_to_model`, `3d_hunyuan3d-v2.1`, multiview, +
`3d_moge_*` panorama/perspective→mesh). Pipeline:

> image → CLIP-vision encode → Hunyuan3D conditioning → KSampler (20 steps, cfg 8, euler/normal)
> → VAEDecodeHunyuan3D (voxel) → VoxelToMesh (surface-net) → SaveGLB

One checkpoint, `hunyuan3d-dit-v2_fp16.safetensors`, bundles MODEL+CLIP_VISION+VAE. The exact
API graph is encoded in `prototypes/run_hunyuan3d.py` (ready to run).

**Model not installed.** `ImageOnlyCheckpointLoader` lists only the SDXL/SD3.5 checkpoints. Action:
download `hunyuan3d-dit-v2_fp16.safetensors` (Comfy-Org/hunyuan3D_2.0_repackaged) into
`ComfyUI/models/checkpoints/`.

Hosted alternatives are also wired (`Tripo*`, `Meshy*`, `Rodin3D*`, `api_hunyuan3d_*`) — paid
APIs, not local-first; a fallback if local proves unworkable.

### ⚠️ License — 3D breaks the clean-Apache lane (Confirmed)

Hunyuan3D 2.0 is the **Tencent Hunyuan Community License**, *not* Apache. Commercial use is
permitted **with conditions**: no redistributing the pretrained model, attribution required, a
large-MAU clause, and — critically — **the license does not apply in the EU, UK, or South Korea**.
So a mesh generated by Hunyuan3D inherits those terms (the Z-Image concept *image* is Apache, but
the *geometry* comes from the Tencent model).

Implication vs. 2D/PBR (fully Apache/MIT): **3D is not automatically clean.**

### Permissive (MIT) alternatives — evaluation (2026-06-22)

| Option | License | Quality | gfx1201 (AMD `ai2`)? | Install |
|---|---|---|---|---|
| **TripoSR** (Stability+Tripo, 2024) | **MIT** incl. weights | low–mid | **likely** | low (Flowty node + 1 model) |
| **TRELLIS / TRELLIS.2** (Microsoft; v2 4B, Dec 2025) | MIT-family | **high** (textured + 3DGS) | **painful/unproven** | high (CUDA wheels) |
| **TripoSG** (VAST-AI) | MIT | high | unknown (lighter than TRELLIS) | medium |
| **MoGe** (installed) | MIT | 2.5D relief only | **already runs** | none |
| Hunyuan3D 2.0 (above) | Tencent (restricted) | high | untested | model only |

- **TripoSR** — fast feed-forward single-image→mesh, mostly standard PyTorch (transformer +
  marching cubes via torchmcubes, which has a CPU fallback) → best ROCm odds and lowest friction.
  Downside: 2024-era fidelity — artifacts on thin features, basic texture; good for
  background/greeble/rocks, not hero assets.
- **TRELLIS(.2)** — the high-quality MIT option (textured meshes + 3D-Gaussian/radiance outputs),
  but **AMD-hostile**: custom-CUDA deps (nvdiffrast, diff-octree/gaussian-rasterization, spconv,
  flash-attn, kaolin). A community ROCm guide exists but is only verified on **gfx1100 (RDNA3)**,
  not gfx1201 (RDNA4) — "strongest on Windows/NVIDIA." Realistically belongs on the **RTX 5070
  workstation** (or the coming 5090/6000), not `ai2`.
- **TripoSG** — newer high-fidelity image-to-3D, lighter deps than TRELLIS; a quality middle-ground.
- **MoGe** (already on `ai2`) — monocular geometry → single-view **2.5D relief** mesh (camera-facing,
  not a closed object); good for terrain/backdrops, testable now with zero install.

**The honest tension:** on the AMD box the clean-licensed options are either *clean + modest*
(TripoSR) or *clean + high-quality but realistically NVIDIA-only* (TRELLIS). Hunyuan was
*high-quality + runs + dirty license*. No free lunch yet — route by hardware.

### ROCm is the open question (Hypothesis)

Whether Hunyuan3D runs on `ai2`'s gfx1201 is **unverified** — image-to-3D stacks sometimes carry
CUDA-only ops (mesh extraction / the voxel VAE). This is the gating test once the model is in.
Fallbacks: the workstation **RTX 5070** (NVIDIA), or hosted, with the ~Aug-2026 5090/6000 ahead.

### Bevy consumption (Supported)

Bevy loads **glTF/.glb natively** (`asset_server.load(GltfAssetLabel::Scene(0).from_asset("x.glb"))`)
— no conversion, unlike the 2D atlas path. But raw image-to-3D output is **high-poly, messy
topology, single baked texture**. For static props that's usually fine after **decimate + UV**
(Blender headless / Instant Meshes); it is *not* animation/rig-ready and not modular (use the
[mechanical-kit](../mechanical-kit/) approach for clean parts).

## Assessment

- **Feasible locally, pending two things:** install the model, then prove it on gfx1201.
- **License is the strategic catch.** Hunyuan3D is fine for prototyping and non-EU/UK/KR commercial
  use with attribution; for a *fully clean* 3D pack, evaluate TRELLIS/TripoSR (MIT).
- Concept-image generation is already solved (Z-Image, Apache) — a clean crate input is staged in
  `prototypes/inputs/`.

## Recommendations

1. **Install** `hunyuan3d-dit-v2_fp16.safetensors` → `models/checkpoints/`.
2. **Run the ROCm test:** `python run_hunyuan3d.py --image inputs/<concept>.png` → expect a `.glb`.
   If it fails on gfx1201, retry on the RTX 5070 workstation; record either way (AMD data point).
3. **Clean-3D path, routed by hardware:** install **TripoSR (MIT)** on `ai2` first — low friction,
   best ROCm odds, a clean lane validated fast (accept modest fidelity for background props).
   Reserve **TRELLIS.2 (MIT, hero quality)** for the **NVIDIA 5070 workstation**, not gfx1201.
   (Hunyuan3D only for prototyping / non-EU-UK-KR use, given the license.)
4. Optionally evaluate **TripoSG (MIT)** as a quality middle-ground; **MoGe** is already installed
   for instant image→relief-mesh terrain/backdrop experiments.
5. Add a cleanup step (decimate/UV) before Bevy import; the in-engine import is a Sounding-side
   work item (like the DWA/PBR imports).

## Open Questions

- Does **TripoSR** run on gfx1201 (ROCm)? — the gating test for the clean lane (likely yes;
  marching-cubes may CPU-fallback). Needs the `ComfyUI-Flowty-TripoSR` node + model installed
  first, then introspect its node API to build the harness.
- Is TripoSR's fidelity enough for the target props, or do we escalate to TRELLIS.2 (NVIDIA) /
  TripoSG?
- Cleanup tooling: headless Blender decimate vs Instant Meshes.
