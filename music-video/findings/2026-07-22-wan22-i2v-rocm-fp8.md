# Findings: Wan2.2 i2v on `ai2` — fp8 falls back to dequantisation on ROCm 6.4

**Date:** 2026-07-22
**Track:** music-video
**Verdict:** fails *(as configured — and the cause is a one-wheel version gap, not the hardware)*

## Goal

Measure how long one ~5-second Wan2.2 image-to-video clip takes on `ai2` (gfx1201 / R9700, 32 GB), to
decide whether motion is a **shot kind** the `music-video` pipeline can budget per shot (~36 clips for
a 3-minute song) or a **hero-shot garnish**.

## Tooling

- **Client:** [`prototypes/generate_clip.py`](../prototypes/generate_clip.py), transcribed from the
  shipped ComfyUI `Image to Video (Wan 2.2).json` blueprint. That blueprint is **subgraph-wrapped** —
  a shallow read shows one opaque node; the real 18-node graph lives in `definitions.subgraphs`.
- **Graph:** `CLIPLoader(umt5_xxl_fp8_e4m3fn_scaled, type=wan)` → pos/neg `CLIPTextEncode`;
  `UNETLoader(high_noise)` and `UNETLoader(low_noise)`, each → `LoraLoaderModelOnly` →
  `ModelSamplingSD3(shift 5)`; `WanImageToVideo(640, 640, 81, 1)`; two `KSamplerAdvanced` stages
  (0→2 high-noise, 2→4 low-noise, `euler`/`simple`, cfg 1); `VAEDecode(wan_2.1_vae)`;
  `CreateVideo(16 fps)`.
- **Input:** `2d/findings/samples-2026-06-22-celestial/dwa_planet.png` (a committed sample — this is a
  cost measurement, not an art test).
- **Negative prompt:** the blueprint's stock Chinese-language default, kept **verbatim** — replacing it
  during a cost measurement would confound cost with a prompt change.

## Hardware

- `ai2`, gfx1201 (R9700), 32 GB VRAM. **ROCm system runtime `rocm-core` 7.2.4.**
- **ComfyUI's torch: `2.9.1+rocm6.4`** (`torch.version.hip = 6.4.43484`), in `/opt/comfyui-env`.

## Result

**`Prompt executed in 00:45:24`** for one 5.06-second clip at 640×640, 81 frames @ 16 fps, 4 steps
with the speed LoRAs. The blueprint's own embedded benchmark claims **≈97 s** for the same
configuration on an RTX 4090D — a **~28× gap**.

The clip *did* complete and is correct in every mechanical respect: `h264`, 640×640, **81 frames**,
`r_frame_rate 16/1`, **5.0625 s**. Exactly what was requested.

**And it is visually unusable.** See below — that is a worse result than a slow one, and it is
reported as such rather than buried under a passing timing number.

### The cause, stated by the software itself

```
[WARNING] FP8 _scaled_mm failed: Float8_e4m3fn is only supported for ROCm 6.5 and above,
          falling back to dequantization
```

68 of these and counting in a single run.

| Component | Version | |
|---|---|---|
| `rocm-core` installed on `ai2` | **7.2.4** | system runtime is comfortably new enough |
| torch in `/opt/comfyui-env` | **`2.9.1+rocm6.4`** | **built against ROCm 6.4** |
| required for native fp8 `_scaled_mm` | **≥ 6.5** | |

**This is not an AMD limitation, a gfx1201 limitation, or a Wan limitation. It is one Python wheel
built 0.1 behind the threshold, on a box whose system ROCm is already 7.2.4.**

`_scaled_mm` **is the matmul**, so the fallback is not confined to model loading — every forward pass
during sampling dequantises too.

### Timing breakdown (second run, high-noise model already resident)

| Phase | Wall-clock |
|---|---|
| Stage 1 sampling — 2 steps, model **cached** | **5 m 37 s** |
| **Stage 2 model load** — low-noise 14 GB, uncached, dequantised | **33 m 55 s** |
| Stage 2 sampling — 2 steps | **5 m 37 s** |
| VAE decode + video mux | 15 s |
| **Total** | **45 m 24 s** |

The two sampling stages agreeing to the second (5 m 37 s each, 2 steps apiece) is a clean measurement:
**~2.8 minutes per sampling step** on a resident model. Even with both models pre-warmed and zero load
cost, a 4-step clip could not go below ~11 minutes.

### The clip is broken — two separate defects

![frames 0, 40 and 80](samples-2026-07-22-wan/frames_0_40_80.png)

**1. The input was an RGBA sprite, and that was our mistake.** `dwa_planet.png` is PNG colortype 6 —
a game sprite with a **transparent background**. `LoadImage` resolves that to something arbitrary, and
frame 0 shows the planet against a white field with black blobs where the alpha was. By frame 40 the
model had invented a starfield to replace it.

This work item's plan said *"any recent harness output is fine — this is a cost measurement, not an
art test."* **That was wrong.** The input choice materially affected the output, and an alpha sprite
is a bad i2v seed regardless of what is being measured — the model spends its capacity resolving a
background that should have been given to it.

**2. The model hallucinated title-card text.** Frame 40 carries `PEONG` across the planet; frame 80 has
`FROMT` in large white letters. Nothing in the prompt (*"slow drifting camera push-in, gentle
parallax, dust motes catching the light, cinematic, subtle motion"*) asked for text. This is the
well-known video-model failure of drifting toward title-sequence semantics on an ambiguous
centred-subject input, and the stock negative prompt (which does list `字幕` — subtitles) did not
suppress it.

Measured corroboration: mean inter-frame luma difference **6.07**, and frame-average luma swinging
**107.7 → 39.8 → 68.7** across frames 0/40/80. A "gentle push-in" holds average luminance roughly
steady; this does not.

**The two-stage MoE architecture is the trap.** Wan2.2 I2V-A14B is a *pair* — high-noise for the first
half of the schedule, low-noise for the second — so **both** 14 GB fp8 checkpoints must be
dequantised. Only one stays comfortably resident in 32 GB (`lowvram patches: 37` appears on the second
load, i.e. they are competing), so the second load is paid on essentially every clip. Caching helps
stage 1 and not stage 2.

Also corroborating: the `umt5_xxl_fp8_e4m3fn_scaled` **text encoder took 5m 40s to load** — it is an
fp8 artifact taking the same path. Two independent symptoms, one cause.

### An earlier confound, recorded because it misled us first

The first attempt ran while a `llama-server` process held **28.0 GB of the 32 GB**, leaving ComfyUI
~3.5 GB. That produced a different failure (partial load, 6.4 GB offloaded, VAE-encode OOM) and an
inversion worth remembering: the **contended** run reached the sampler *faster*, because with little
VRAM ComfyUI offloaded most of the model rather than casting and placing all of it.

This also corrects WI 989's survey note of "~27 GB of ai2's 32 GB in use", which was read as a
pageable model. It was a resident service.

## Repeatability

Deterministic and reproducible: the fallback fires on every fp8 matmul, every run. Nothing here is
flaky — it is uniformly slow.

## Assessment

**Verdict for the pipeline, as configured today: video is neither a shot kind nor a garnish — it is
unusable.** ~45 min/clip × ~36 clips ≈ **27 GPU-hours** per full-motion render, per iteration.

**But the constraint is specific and fixable, and it is worth separating from the hardware.** On the
same box, ACE-Step 1.5 produced 75 s of 48 kHz vocal audio in 117 s, and the 2D tracks run there
routinely. `ai2` is fine for audio and images. It is fp8 that is broken here.

**Scope beyond this track:** this affects **every fp8 model on `ai2`**, not just Wan. Because the
fallback is a *warning* and not an error, it degrades silently — any track reaching for an `_fp8_` or
`_fp8_scaled` checkpoint on that box has been paying it without a failure to notice.

## Next

1. **Upgrade torch in `/opt/comfyui-env` to a ROCm ≥ 6.5 build** — the system runtime is already
   7.2.4, so this is a wheel swap, not a driver or system upgrade. Highest value: it fixes fp8 for the
   whole box. **Owner decision — it modifies a shared service environment.**
2. **Or use the `fp16` Wan checkpoints** (28.6 GB each, both already on the box). No fp8 ops, no
   fallback. Costs more VRAM and helps only Wan. `generate_clip.py` needs two constants changed.
3. **Re-measure after either**, and only then answer the shot-kind-vs-garnish question the spike was
   filed to answer. The client is written and ready.
4. **Until then, WI 1004 should assume stills-plus-Ken-Burns only**, with no Wan clip. That was already
   the recommended hybrid; this makes it the only option.
5. **When i2v is re-attempted, two input rules now apply, learned the expensive way:**
   - **Feed opaque stills only.** No RGBA, no transparent background. If a sprite is the source,
     composite it onto a real background *first* — the model should be given the background, not
     asked to invent one.
   - **Expect text hallucination on centred-subject inputs.** The stock negative prompt lists
     subtitles and did not prevent it. Budget a rejection rate, or strengthen the negative, or avoid
     compositions that read as title cards.
   Neither of these is about ROCm, and both will still be true after the wheel is fixed.
5. Consider whether the RTX 5070 workstation (12 GB, CUDA, **no ComfyUI installed**) is worth
   provisioning as a video host. Above the fp8 minimum, and CUDA has no equivalent of this gap.
